# Dataset Guide

## Manifest schema (used by the benchmark module)

The benchmark module (`app/services/benchmark_service.py`, exposed via `POST /api/benchmark/run`
and `evaluation/benchmark.py`) reads a **CSV or JSONL manifest** with one row/line per sample:

| Field | Required | Description |
|---|---|---|
| `image_path` | Yes | Path to the image, relative to the manifest file's directory (or absolute). |
| `reference_text` | Yes | Ground-truth transcription of the handwritten content. |
| `expected_answer` | No | The correct final answer, if this sample is used for diagnosis-accuracy scoring. |
| `mistake_label` | No | One of the categories in `app/services/diagnosis.py::CATEGORIES`, if this sample is used for diagnosis-accuracy / macro-F1 scoring. |
| `sample_id` | No | A human-readable ID; defaults to `image_path` if omitted. |

### JSONL example

```jsonl
{"sample_id": "s001", "image_path": "images/s001.png", "reference_text": "12 + 15 = 27", "expected_answer": "27", "mistake_label": "correct_solution"}
{"sample_id": "s002", "image_path": "images/s002.png", "reference_text": "-3 + 5 = -8", "expected_answer": "2", "mistake_label": "sign_error"}
```

### CSV example

```csv
sample_id,image_path,reference_text,expected_answer,mistake_label
s001,images/s001.png,12 + 15 = 27,27,correct_solution
s002,images/s002.png,-3 + 5 = -8,2,sign_error
```

The bundled `evaluation/manifests/demo_manifest.jsonl` follows this schema and points at the
synthetic images generated by `backend/scripts/generate_demo_images.py` — useful for smoke-testing
the pipeline, **not** a real evaluation set (see below for that).

## Adding IAM data

The [IAM Handwriting Database](https://fki.tic.heia-fr.ch/databases/iam-handwriting-database) is
a standard handwritten-text-line benchmark, but it is distributed under a research license that
does not permit redistribution. To use it here:

1. Register for access and download IAM yourself from the official source.
2. Do **not** commit IAM images or transcriptions into this repository.
3. Convert IAM's line-level ground truth (`lines.txt` / `words.txt`) into the manifest schema
   above — write a small one-off script that reads IAM's format and emits JSONL rows with
   `image_path` pointing at your local IAM copy and `reference_text` set from IAM's transcription
   field. `mistake_label` / `expected_answer` won't apply to raw IAM lines unless you're
   specifically testing transcription quality (CER/WER) rather than diagnosis accuracy.
4. Place the resulting manifest under `evaluation/manifests/` (this path is gitignored for
   anything you name outside the bundled demo manifest — check `.gitignore` if you want to keep
   it out of version control) and point `evaluation/benchmark.py --manifest` at it.

## Adding CROHME data

[CROHME](https://www.isical.ac.in/~crohme/) (Competition on Recognition of Online Handwritten
Mathematical Expressions) is more directly relevant to this project's math-heavy scope, and is
distributed under its own competition terms — again, download it yourself and do not
redistribute it via this repository.

CROHME ground truth is typically in InkML (stroke-level) or LaTeX form, not raster images —
you'll need to (a) render each InkML sample to a PNG (there are open InkML-to-image converters),
and (b) convert the LaTeX ground truth to a plain-text approximation that matches how a student
would write it linearly (e.g. `\frac{1}{2}` → `1/2`) since this project's SymPy-based parser
targets linear notation, not full LaTeX. Document any conversion lossiness in your manifest
generation script.

## Adding your own custom annotations

The simplest path for a classroom pilot: photograph real (anonymized, consented) student work,
manually transcribe each sample, and manually label the mistake category using the categories in
`app/services/diagnosis.py::CATEGORIES`. Store images under a directory of your choice and write a
manifest JSONL/CSV pointing at them. This is exactly the workflow `scripts/seed_demo_data.py`
follows at a tiny scale for the bundled demo samples.

## Component summary: what's learned vs. deterministic

Per the project brief's request for a short explanation of which components use pretrained deep
learning vs. deterministic software logic:

| Component | Pretrained deep learning? | Notes |
|---|---|---|
| Image preprocessing | No | Classical OpenCV operations (CLAHE, adaptive threshold, etc.) |
| Region detection | No | Contour-based heuristic segmentation |
| Demo OCR provider | No | Hash-matched lookup table, explicitly mock |
| TrOCR provider | **Yes** | Real HuggingFace `VisionEncoderDecoderModel` inference |
| Donut provider | **Yes** | Real HuggingFace `VisionEncoderDecoderModel` inference |
| Vision-API provider | **Yes** (hosted) | Real Claude / OpenAI-compatible vision-LLM API call |
| Math parsing/verification | No | SymPy symbolic parsing, no learned component |
| Mistake diagnosis (default path) | No | Deterministic rule-based classification |
| Mistake diagnosis (fallback path) | Architecturally LLM-capable | Only reached when all steps are unparseable; returns an honest "insufficient information" result in this build (see `MODEL_COMPARISON.md`) |
| Feedback generation | No | Deterministic templates keyed by diagnosis category |
| Quiz generation | No | Deterministic templates, seeded RNG for numeric variation |
| Mastery update | No | Documented EMA formula |
